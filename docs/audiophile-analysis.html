Audiophile API — System Analysis & Design

Audiophile API · System Analysis & Design · Aug 2026

The four drawings that let you explain this system to anyone.

Use cases say who wants what. Sequence diagrams say in what order, and who talks to whom. The ERD says what is stored and how it relates. The class diagram says what the code believes. Each answers a question the others can't — and where two of them disagree, you've found a bug before writing it.

00 · Orientation

What each diagram is for

These come from UML and from database modelling. You don't need all of UML — four notations carry almost every conversation you'll have about a system like this.

DiagramAnswersReads asYou use it to
Use case Who uses the system, and to do what? Stick figures (actors) connected to ovals (goals) inside a system boundary Agree on scope. Spot a missing actor — external systems are actors too.
Use case spec What exactly happens in one use case, including when it goes wrong? A form: actor, preconditions, main flow, alternate flows, postconditions Find the requirement nobody wrote down. Most bugs live in the alternate flows.
Sequence In what order do the parts talk, and who waits for whom? Vertical lifelines, time flowing down, horizontal arrows as messages Find blocking calls, missing transactions, and race windows.
ERD What is stored, and how are the tables related? Boxes as tables, crow's-foot lines showing one-to-many Check keys, cardinality, and whether a delete will orphan rows.
Class What does the code think the model is? Boxes with fields and methods, lines for composition and reference See aggregate boundaries — which the ERD cannot show at all.
State What states can one thing be in, and which changes are legal? Rounded boxes, arrows labelled with the event that causes the change Prove there's no path to an impossible state.

The most useful thing on this page

An ERD and a class diagram of the same system look different on purpose. The ERD has no way to draw an aggregate boundary — to Postgres, CartItems is just a table you can query directly. The class diagram shows that CartItem is unreachable except through Cart. Both are true; they describe different layers. Confusing them is how people end up with a repository per table and no domain model left.

Three gaps this table exposes

  • UC-04 has no requirement ID. Your plan describes registration (M2-06) and refresh (M2-01) but never states what login must do. It's the most-used endpoint in the system and it's undocumented.
  • Nothing refunds. UC-14 cancels and restores stock, but no use case touches Payment.Refund(). A customer who paid by card and cancels gets their stock back to the shop and nothing back to their card.
  • No admin actor for refunds or customer support. Real shops need "admin cancels on behalf of customer". Out of scope is a fine answer — but decide it rather than discover it.

02 · Specifications

The two use cases worth writing out in full

A use case spec is where you find the requirement nobody wrote down, because it forces you to enumerate the ways things go wrong. Notice how much longer the alternate flows are than the main flow — that ratio is normal, and it's the whole value of the exercise.

UC-11 Place order domain only
Actor
Customer (authenticated)
Goal
Turn the current cart into a durable order with frozen prices and a shipping snapshot.
Preconditions
  • Caller holds a valid access token.
  • Cart is non-empty and belongs to the caller.
  • The chosen address exists, is active, and belongs to the caller.
  • An Idempotency-Key header is present.
Main flow
  1. System checks whether the idempotency key has been seen. It has not.
  2. System opens a transaction.
  3. System loads the cart with its lines, and loads each product fresh.
  4. System builds an OrderLine per cart line, taking price and name from the product.
  5. System decrements stock on each product.
  6. System snapshots the address into ShippingDetails and calls Order.Place, which derives all totals.
  7. System clears the cart.
  8. System commits.
  9. If paying by card, system creates a Stripe PaymentIntent and keeps its client secret.
  10. System returns 201 Created with the order id and, for card, the client secret.
Alternate flows
  • A1 · Key already seen, same request. Return the original order with 200 OK. Create nothing.
  • A2 · Key already seen, different request. Return 409 Conflict. (My addition — the plan doesn't cover this.)
  • A3 · Insufficient stock at step 5. Roll back. Return 409 naming the product.
  • A4 · Concurrent checkout won the row. DbUpdateConcurrencyException at commit. Retry once from step 3; on second failure return 409.
  • A5 · Cart empty. Return 400. Order.Place would throw anyway — fail earlier with a better message.
  • A6 · Address not the caller's. Return 404, not 403 — don't confirm that someone else's address id exists.
  • A7 · Stripe unreachable at step 9. Order is already committed as Pending. Return 201 without a client secret and let the customer retry payment. Do not roll back a valid order because a third party is down.
Postconditions
Order exists as Pending; stock is decremented; cart is empty; the idempotency key is recorded. Payment is not taken yet.
UC-12 Confirm payment (Stripe webhook) domain only
Actor
Stripe («external system») — this actor calls you
Goal
Move an order from Pending to Confirmed when the card actually cleared.
Preconditions
Endpoint is publicly reachable. Signing secret is configured. An order exists with the referenced PaymentIntent id.
Main flow
  1. Stripe POSTs an event with a signature header.
  2. System verifies the signature against the raw request body.
  3. System finds the payment by PaymentIntent id.
  4. System calls MarkSucceeded(), which returns true.
  5. System confirms the order and saves.
  6. System returns 200 OK quickly.
Alternate flows
  • A1 · Duplicate delivery. MarkSucceeded() returns false; Order.Confirm() is a no-op. Still return 200 — a non-200 makes Stripe retry forever.
  • A2 · Bad signature. Return 400 and log it. Never trust the body.
  • A3 · Unknown PaymentIntent. Return 200 and log. It may be an event for a different environment sharing the endpoint.
  • A4 · Payment failed event. MarkFailed(). Order stays Pending so the customer can retry. Open question: who restores the stock, and when?
  • A5 · Events arrive out of order. A succeeded after a failed throws today, because your transition table forbids it. Decide whether that's correct.
Postconditions
Payment is Succeeded and order is Confirmed — exactly once, regardless of how many times the event arrived.

What writing these just surfaced

Three real decisions your build plan never mentions, all found by enumerating alternate flows rather than by writing code: A7 (Stripe down after commit), A4 (stock held by an abandoned failed payment — a real shop's inventory quietly leaks here), and A5 (out-of-order events hitting a transition table that forbids them). Answer all three before Phase 4.

04 · Data

Entity relationship diagram

Crow's-foot notation: a single tick means "exactly one", the three-pronged foot means "many". Read each line as a sentence in both directions — one user has many orders; one order belongs to one user.

Delete behaviour — decide each one

Your plan says "delete behaviour chosen per relationship, each with a comment saying why". Here's the reasoning to write down:

  • User → Cart, CartItems, RefreshTokens, Addresses: Cascade. Meaningless without their owner.
  • User → Orders: Restrict. Orders are financial records. Deleting a user must not erase sales history.
  • Product → CartItems: Cascade. A delisted product should leave carts.
  • Product → OrderItems: Restrict. Never destroy what was sold.
  • Order → OrderItems, Payment: Cascade. Genuinely part of the order.

Why the ERD can't tell the whole truth

Postgres will happily let you INSERT INTO "CartItems" directly. Nothing in this diagram stops you. The rule that cart lines are only ever created by Cart.AddItem lives in C#, not in the schema — which is exactly why the unique index on (CartId, ProductId) matters. It's the database's independent enforcement of a rule the domain also enforces. Belt and braces, deliberately.

What this table proves, and what it doesn't

Every use case except UC-04 has a domain method that enforces its rules, and those methods are covered by the 54 checks that pass against your entities. That's the good news.

What it doesn't prove: nothing here has ever touched a database. Every "verified by domain check" is verified in memory, with no EF mapping, no transaction, and no concurrency. The three items marked in orange — the checkout race, webhook replay end to end, and "can user A read user B's orders" — cannot be verified without the integration tests, and they are the three most likely places for a real bug.
