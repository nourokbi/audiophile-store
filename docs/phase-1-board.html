The Persistence Phase

Audiophile API · Phase 1 · M1-03 … M1-12

Get the model into Postgres, then prove one request works.

Twenty-one tasks in five stages, ordered by dependency. You write all of it; I review, point at the bug without fixing it, and answer "why is it done this way". Stage B is three-quarters of the value in this phase — everything else is downstream of getting the schema right.

Two habits, both cheap

Predict first

Before each task, write one line saying what you think the answer is. A wrong prediction followed by the right answer sticks; the right answer alone slides off. Costs ninety seconds.

Twenty minutes

Stuck past twenty minutes with no new information? Ask. That's not quitting, it's the correct trigger — past that point you're not learning, you're just stuck.

How to ask

"Review B3." · "Why doesn't my ValueComparer fire?" · "Is this the right seam?" I'll tell you where to look rather than hand you the patch.

Say "write it" when

It's boilerplate with nothing to teach, or you're stuck past the point of learning. Both are legitimate — just say so and I'll take it.

STAGE A ~1 hour

Clear the decks

Small, boring, blocking. The Identity decision left debris — remove it before you build on top of it.

A1 Delete what Identity made redundant
  • Delete src/Audiophile.Application/Abstractions/IPasswordHasher.cs
  • Remove BCrypt.Net-Next from Audiophile.Infrastructure.csproj

Identity ships IPasswordHasher<TUser> and UserManager owns hashing. Two hashing paths is how you end up with accounts that can't log in.

Done when

dotnet build is clean and BCrypt appears in no .csproj.

A2 Move UserSecretsId to the API project

What user-secrets is. A per-developer JSON file that lives outside the repo, at %APPDATA%\Microsoft\UserSecrets\<id>\secrets.json. It keeps a connection-string password or a JWT signing key off disk-in-git while still making it available in Development. It is not encrypted and it is not for production — production reads environment variables or a key vault.

What the UserSecretsId property does. That GUID is the folder name. At build time the SDK turns it into an assembly-level attribute:

[assembly: UserSecretsId("08c0f11e-a187-4da6-bb8b-afbaa4a8f788")]

Why it must sit on API, not Infrastructure. WebApplication.CreateBuilder(args) loads user-secrets by reading that attribute off the entry assembly — the one with Main, which is Audiophile.API.dll. Today the attribute is baked into Audiophile.Infrastructure.dll, where nothing ever looks for it.

What that actually costs you
  • Audiophile.API.dll carries no id → CreateBuilder finds nothing → no secrets are loaded at all
  • no error, no warning, no log line
  • builder.Configuration["ConnectionStrings:Postgres"] returns null, and you meet it as a NullReferenceException or a "host cannot be null" from Npgsql — several layers from the cause
  • dotnet user-secrets set … -p src/Audiophile.API fails outright, because the CLI needs the id on the project you point it at

The edit: cut the <UserSecretsId> line out of Audiophile.Infrastructure.csproj and paste it into the <PropertyGroup> of Audiophile.API.csproj. Keep the same GUID and the existing secrets folder comes with it — there's already a secrets.json there from an earlier session.

Done when

dotnet user-secrets list -p src/Audiophile.API runs without error, and Audiophile.Infrastructure.csproj no longer mentions secrets.

A3 Apply the role decision — Identity roles win

Decided 18 Aug 2026. ASP.NET Core Identity owns roles. The UserRole enum comes out of the domain; AspNetRoles / AspNetUserRoles become the source of truth. Roles are read with UserManager.GetRolesAsync and emitted as claims when the JWT is built in Milestone 2.

I'd recommended the enum. You chose Identity — it's the more conventional answer, it's what [Authorize(Roles=…)] expects natively, and adding a third role later becomes a data change instead of a migration. Noted and moving on.

Three edits, in this order:

  1. Domain/Entities/User.cs — remove Role, IsAdmin, PromoteToAdmin, DemoteToCustomer; drop the UserRole role parameter from the private constructor; collapse Register and CreateAdmin into one Create(name, email) factory
  2. Delete Domain/Enums/UserRole.cs
  3. Add Application/Common/Roles.cs — const string Admin and Customer, so neither [Authorize] nor the seeder uses a magic string. Application rather than Domain: roles are now an authorization concern, and the domain no longer knows what a role is.
The conceptual shift — the real content of this task

Role used to be an intrinsic property set at construction: User.CreateAdmin(…) produced an admin in one atomic step. It is now a relationship row created after the user exists. Making an admin becomes two operations that can partially fail — which is why E1 gets more careful.

What you give up

The domain can no longer answer "is this an admin". Nothing in the domain asks today, so the cost is zero right now — but if a domain rule ever needs it, it has to be told rather than ask.

Done when

dotnet build is clean, grep -r UserRole src/ returns nothing, and docs/build-plan.md records the decision.

A4 Fix the README's false rule

README.md says Domain references nothing. Domain now carries Microsoft.AspNetCore.Identity.EntityFrameworkCore. Amend the rule to state the one exception and its reason.

Why it matters more than it looks

A rule the repo openly breaks trains you to ignore rules. Either it's true, or it's documentation debt.

STAGE B 1–2 days

Persistence

This is the phase. Decision-dense, and where I'd have you spend most of your time.

B1 Connection string and user-secrets

appsettings.json currently has no ConnectionStrings section at all.

  • The key goes in appsettings.json with a local-dev-only value
  • Anything real goes in user-secrets: dotnet user-secrets set "ConnectionStrings:Postgres" "…" -p src/Audiophile.API
Done when

You can print the resolved connection string from Program.cs.

B2 Write AppDbContext

src/Audiophile.Infrastructure/Persistence/AppDbContext.cs. Three things to get right:

  1. Base class — IdentityDbContext<User, IdentityRole<Guid>, Guid>, per the A3 decision. Not DbContext, and not IdentityUserContext — that one omits the very role tables you've just decided to use. It brings seven tables you didn't write: AspNetUsers, AspNetRoles, AspNetUserRoles, AspNetUserClaims, AspNetUserLogins, AspNetUserTokens, AspNetRoleClaims. Expect them in the migration — their presence is how you know the base call ran.
  2. base.OnModelCreating(builder) must be the first line of your override.
  3. builder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly) so you never have to remember to register a configuration class.
Trap

Skip the base call and Identity's own table configuration never runs. Your first migration is garbage, and hand-editing it isn't worth attempting — you'd delete and start over.

A real decision — which types get a DbSet<T>?

Only aggregate roots: Product, Order, Cart, Address, and User via Identity. Not CartItem, OrderItem, RefreshToken, Payment — they're reachable only through their root, and a DbSet is an open invitation to query around the aggregate boundary you spent yesterday building.

EF still maps them; it discovers them through the navigations. A missing DbSet costs you nothing and buys you an enforced boundary.

Predict first

If you leave out DbSet<CartItem>, does CartItem still get a table? Write your answer down, then check the migration.

Done when

dotnet ef dbcontext info -p src/Audiophile.Infrastructure -s src/Audiophile.API succeeds.

B3 ProductConfiguration — start here

Product is the densest entity in your model. Do it first; everything after is easier.

  • Price → decimal(18,2)
  • Category → .HasConversion<string>() — readable in psql, and it survives someone reordering the enum
  • Name, Description, Features → max lengths matching the consts already on the entity
  • InTheBox → jsonb, through the backing field, with a ValueComparer
  • UseXminAsConcurrencyToken() — the Npgsql extension. Creates a shadow property; you never declare xmin on the entity.
  • CHECK constraints: Stock >= 0, Price > 0
  • Index on Category, and on IsActive if you'll filter by it
Three traps, worst first
  1. No ValueComparer → EF never notices you changed the dictionary. You call PutInBox, SaveChanges reports zero rows affected, and nothing errors. Silent data loss is the worst failure mode there is.
  2. The snapshot lambda must rebuild with StringComparer.OrdinalIgnoreCase. The entity deliberately uses a case-insensitive dictionary. A snapshot built with the default comparer quietly loses that, and "Headphone Unit" vs "headphone unit" become two entries again.
  3. InTheBox has no setter — it's IReadOnlyDictionary over _inTheBox. Point EF at the field or it can't materialise a loaded product.
Predict first

What is the equality half of the comparer, for a dictionary where key order doesn't matter? Write it before you look it up.

Done when

You load a product, call PutInBox("Cable", 2), SaveChanges, reload in a fresh context — and the cable is there.

B4 Cart and CartItem
  • Backing field _cartItems for the CartItems navigation
  • Unique index on (CartId, ProductId) — the database half of the rule Cart.AddItem enforces in memory. Both halves, always.
  • Unique index on Cart.UserId — one cart per user
  • CHECK: Quantity BETWEEN 1 AND 100, mirroring CartItem.MaxQuantity
  • Delete behaviour: User → Cart and Cart → CartItem cascade; CartItem → Product restrict
Why restrict on CartItem → Product

Cascading would silently empty people's carts when an admin deletes a product. Restrict turns that into a loud error — at which point you'll realise products should be deactivated, not deleted, which is exactly why Product.Deactivate() exists.

B5 Order, OrderItem, Payment
  • All money → decimal(18,2): SubTotal, DiscountAmount, ShippingFee, TotalAmount, UnitPrice, Payment.Amount
  • Status, PaymentMethod, PaymentStatus → strings
  • Unique index on Order.IdempotencyKey — M4-04 depends on this existing
  • Order ↔ Payment one-to-one, FK on Payment.OrderId
  • Snapshot columns ShippingFullName … ShippingPostalCode — plain columns, postal code nullable, the rest required
  • Delete behaviour: Order → OrderItem and Order → Payment cascade; User → Order and OrderItem → Product restrict
Why restrict on User → Order

An order is a financial record. Deleting a user must not erase what they bought. This forces you to think about account deletion properly later, rather than discovering the problem in production.

Trap

Don't give UpdatedAt a database default or trigger. Order.Touch() already owns it, and two writers for one column is a drift you'll debug at the worst time.

B6 User, Address, RefreshToken
  • Three backing-field collections on User: _addresses, _orders, _refreshTokens
  • User ↔ Cart one-to-one, required — the User constructor creates it, so "user without a cart" must be unrepresentable in the database too
  • Unique index on RefreshToken.Token; plain index on RefreshToken.UserId
  • Address.IsActive — soft delete
After A3, there is no Role column to configure

AspNetUsers gets Name and CreatedAt from you and nothing else role-shaped. Roles live in AspNetUserRoles, which base.OnModelCreating configures entirely. Don't write a configuration class for the Identity tables — you'd be fighting code that already works.

Something I'd push back on

A global query filter on Address.IsActive. It looks clean, and then it silently hides rows in the one place you needed them — admin views, order-history joins — with no compiler error. User.FindAddress already filters. Skip the global filter.

B7 Verify the model before you migrate

Do not skip this. Five minutes, and it catches the expensive mistakes.

  • dotnet ef dbcontext info succeeds
  • Dump the model debug view and actually read it
  • Find the line proving CartItems uses the field _cartItems, not the property
Trap

If EF quietly picked the property instead of the field, every collection in your model is broken — and the migration will still look completely fine.

Done when

You can point at the specific line in the debug view that proves field access. Not "it probably worked."

B8 First migration 
dotnet ef migrations add InitialCreate \
  -p src/Audiophile.Infrastructure \
  -s src/Audiophile.API

Read the generated migration line by line before you apply it. This is the highest-value review in Phase 1 — the first time your intent and EF's interpretation are visible side by side.

Check specifically:

  • InTheBox is jsonb, not text
  • money columns are numeric(18,2), not bare numeric
  • enum columns are text, not integer
  • xmin appears nowhere as a real column — it's a system column, so if EF tried to create one, your concurrency config is wrong
  • the Identity tables are present and sane
  • unique indexes exist for (CartId, ProductId), Cart.UserId, RefreshToken.Token, Order.IdempotencyKey
Done when

dotnet ef database update succeeds, and \d products in psql matches what you intended — column by column.

STAGE D ~1 day

Cross-cutting

D1 ProblemDetails middleware M1-05
The decision here

Your domain throws framework exception types — ArgumentException, InvalidOperationException, ArgumentOutOfRangeException. Do you map those directly, or introduce domain exception types?

Map them for now, and note the tension: InvalidOperationException is doing double duty — "insufficient stock" (→ 409) and "illegal status transition" (→ 422) are the same C# type with different HTTP meanings. You'll feel that in Phase 4, and that is the right moment to introduce DomainException subtypes, with concrete cases instead of speculation.

A starting map: ArgumentException → 400 · KeyNotFoundException → 404 · InvalidOperationException → 409 · DbUpdateConcurrencyException → 409 · everything else → 500.

Trap

Returning ex.Message for an unhandled exception leaks connection strings and table names to the internet. Suppress the message outside Development.

D2 FluentValidation validators M1-06, M1-07

Write the validators and register them in DI. Do not wire the automatic MVC integration. M3-03 moves validation into a MediatR pipeline behavior — wiring it twice means writing code you'd delete. You still learn FluentValidation here; you just skip the throwaway part.

D3 Serilog and a correlation id M1-08

Structured logging means Log.Information("Order {OrderId} placed", id) — a queryable field, not string concatenation. The correlation id goes in a middleware early in the pipeline and into the log context for the whole request.

D4 GET /health with a database check M1-09

Add AspNetCore.HealthChecks.NpgSql. Health must actually open a connection — a check that returns 200 while the database is down is worse than no check at all, because something downstream will trust it.

D5 CORS from configuration M1-10

Origin list read from config. Never AllowAnyOrigin() alongside credentials — the browser rejects that combination outright, which is a good hint that it was always wrong.

D6 Forwarded headers before the rate limiter M1-11

Write out your full middleware order and justify each position. Then check it against these three:

  • UseForwardedHeaders before anything that reads the client IP
  • UseAuthentication before UseAuthorization — one populates what the other reads
  • exception handling first, so it can catch everything after it
Why the plan calls this non-optional

The rate limiter partitions on RemoteIpAddress. Behind any reverse proxy — which is every real deployment — that's the proxy's address, so every user on earth shares one bucket. Works perfectly locally. Fails completely in production.

STAGE E ~1 hour

Admin seeder

E1 Seed an admin from configuration M1-12

After A3 this is three idempotent steps rather than one, each able to fail on its own:

  1. RoleManager.RoleExistsAsync → CreateAsync for Admin and Customer
  2. UserManager.FindByEmailAsync → CreateAsync for the admin user
  3. UserManager.AddToRoleAsync(user, Roles.Admin)
  • Reads email and password from configuration — user-secrets, not appsettings.json
  • Goes through UserManager.CreateAsync, never DbContext.Add
  • Check IdentityResult.Succeeded after every call — these methods return failures, they don't throw. Ignoring the result is how you get a seeder that logs nothing and seeds nothing.
The partial failure A3 created

Step 2 succeeds, step 3 fails, and you're left with a user who has no role — an account that exists, can log in, and can do nothing. Make the seeder re-entrant so the next startup repairs it: don't skip step 3 just because the user already exists.

Trap

Inserting a User straight through DbContext leaves NormalizedEmail and SecurityStamp null. Nothing errors. The row looks fine in psql. Login then fails forever with no useful message, because UserManager looks users up by NormalizedEmail.

Why this unblocks everything

Without it, every admin endpoint is unreachable on a fresh database and you can't test M1-07 or anything in Milestone 4.

Phase 1 is done when

  1. dotnet ef database update on an empty database produces the full schema
  2. dotnet run starts clean
  3. GET /health returns 200 — and genuinely fails when you stop Postgres
  4. GET /products returns seeded products
  5. A deliberately broken request returns a ProblemDetails body, never a stack trace
  6. You can log in as the seeded admin
  7. You can explain, without notes, why OrderItem → Product is Restrict

Item seven isn't filler. If you can't answer it out loud, the model isn't in your head yet — and Phase 4 is where that costs you.

One thing to carry into Milestone 2

You said you'll put the role in the JWT. When you get there, this is the trap that eats an afternoon.

[Authorize(Roles = "Admin")] does not look for a claim called role. It looks for ClaimTypes.Role, which is the URI http://schemas.microsoft.com/ws/2008/06/identity/claims/role. Write "role" as your claim type when building the token and authorization silently fails — a valid token, the correct role in the database, and a 403 with nothing in the logs.

Two ways out. Pick one and be consistent:

  • emit the claim as ClaimTypes.Role, or
  • emit short "role" and set TokenValidationParameters.RoleClaimType = "role"
Why this bug is so common

JwtSecurityTokenHandler rewrites short claim names to those long URIs by default; the newer JsonWebTokenHandler doesn't. Two handlers, two different defaults, and the tutorial you're reading probably used the other one. Decide explicitly whether MapInboundClaims stays on.

Where I'd expect you to get stuck

Ranked by likelihood, so you know it's normal rather than a sign you're lost.

1 The InTheBox ValueComparer — nearly everyone gets a silently-not-saving dictionary the first time B3 · silent
2 Backing fields not picked up — no error, and the migration looks correct anyway B7 · silent
3 Identity with a Guid key, and the missing base.OnModelCreating B2 · loud
4 Middleware order — fine locally, broken behind a proxy D6 · silent

Three of the four fail silently. That's the real lesson of this phase: the persistence layer rarely tells you it's wrong — it just quietly does something else.
