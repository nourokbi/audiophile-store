Five corrections to the build plan

Your plan was written before the Identity decision. That decision is fine — but it has consequences the plan doesn't know about yet. Fix these in docs/build-plan.md before you write more code, or you'll follow instructions that no longer apply.

1. Identity is no longer deferred — the plan still says it is

The plan lists "ASP.NET Core Identity migration" under Deliberately deferred, with the reasoning "best done when checkout is finished". You did it on day one instead. That's a defensible call, but three downstream instructions are now wrong:

  • IPasswordHasher (the M1-01 note) is dead. Identity ships IPasswordHasher<TUser> and UserManager owns hashing. Delete the file.
  • The M1-12 seeder can no longer insert a user through DbContext. It must go through UserManager, or NormalizedEmail and SecurityStamp stay null and login silently fails.
  • AppDbContext is now IdentityDbContext<User, IdentityRole<Guid>, Guid>, not DbContext. Get this wrong and your first migration is unrecoverable-by-hand.

2. The README's "Domain references nothing" rule is now false

README.md says Domain has no packages and "if you ever need to add one there, something has leaked into the wrong layer." Domain now carries Microsoft.AspNetCore.Identity.EntityFrameworkCore. Don't leave a rule in the repo that the repo breaks — amend it to state the one exception and why. A rule with a silent exception teaches you to ignore rules.

3. You now have two role systems. Pick one.

User.Role is your UserRole enum. Identity also brings IdentityRole<Guid>, RoleManager, and [Authorize(Roles = "Admin")]. Running both means the enum and the role table can disagree about who is an admin, and you will find out via a security hole rather than a compiler error.

My recommendation: keep the enum as the single source of truth (it's simpler, it's already in the domain, and you have exactly two roles), and emit it as a claim when you build the JWT. Then [Authorize(Roles="Admin")] reads your claim and no Identity role table is needed. Decide this in Phase 1, not Phase 4.

4. M1-06 and M3-03 make you build validation twice

M1-06 says wire FluentValidation into the request pipeline. M3-03 then says move it into a MediatR pipeline behavior. That's the same work twice — you'd write the auto-validation wiring, then delete it.

Change: in Phase 1, write the validators and register them, but don't wire the automatic MVC integration. Call them manually or leave them unused for one phase. Wire them once, in Phase 3, where the behavior belongs. You still learn FluentValidation in Phase 1; you just don't learn the throwaway part.

5. Two real gaps in M4 that nothing covers

  • M4-04 doesn't say what happens on key reuse with a different cart. "Same idempotency key returns the original order" is right when the request matches. When the same key arrives with a different body, returning the old order is a lie. Add: mismatched body on a seen key returns 409.
  • Nothing refunds a cancelled paid order. M4-14 restores stock but never touches the payment. Your Payment.Refund() exists and no requirement calls it. Add a requirement, or state explicitly that refunds are manual and out of scope — either is fine, silence isn't.
PHASE 0 done

What you already built, and what it's called

You've used five named patterns in the last hour. Knowing their names matters — it's how you find the literature, and it's what an interviewer is listening for.

Rich domain model

Data and the rules about that data live in the same class. The opposite — public setters plus a service that knows the rules — is the anemic domain model, named by Fowler as an anti-pattern.

Aggregate & aggregate root

A cluster of objects treated as one unit for changes. Cart is a root; CartItem is inside it and unreachable from outside. From Evans' Domain-Driven Design.

Value object

ShippingDetails and OrderLine have no identity — two with the same fields are the same thing. That's why they're records and why equality is structural.

Guard clause / precondition

Reject bad input at the top and leave the happy path unindented. Fowler's refactoring catalog; the deeper idea is Meyer's Design by Contract.

State machine

Order.AllowedTransitions is a transition table. Making illegal states unrepresentable is the whole point — there is no path to a shipped-then-cancelled order.

Snapshot / denormalization

Order copies the address instead of referencing it. Deliberate duplication, because history must not change when the present does.

PHASE 1 start here

Persistence and a working request

Plan reference: M1-03 through M1-12. The goal is a database your model actually maps to, and one endpoint that proves the whole stack is wired. Everything after this phase assumes you can save an entity.

New concepts in this phase

Dependency inversion

Why API may reference Infrastructure without breaking Clean Architecture. The reference exists so Program.cs can bind an interface to a class — and for nothing else.

Backing-field mapping

EF must write to _cartItems, not CartItems, because you exposed the collection read-only. EF finds it by convention — verify, don't assume.

Owned types & converters

How InTheBox becomes a jsonb column, and why it needs a ValueComparer or EF will not notice your edits.

ProblemDetails (RFC 7807)

One machine-readable error shape for the whole API, instead of every endpoint inventing its own.

Structured logging

Serilog logs fields, not sentences. {OrderId} becomes a queryable property, not string concatenation.

PHASE 2 after 1

Auth, and the gap that makes rotation real

Plan reference: M2-01 through M2-06. Small, self-contained, and worth doing before anything is built on top of auth. Identity handles registration and password hashing; refresh tokens are still yours, because Identity doesn't do them.

New concepts in this phase

Access vs refresh token

Short-lived bearer credential vs long-lived right to get a new one. They fail differently and are stored differently.

Rotation

Every refresh invalidates the token presented and issues a new one. Halves the window a stolen token is useful for.

Reuse detection

The other half. A token presented twice is proof of theft, because the legitimate client threw its copy away.

Token family

All tokens descended from one login. The unit you revoke when reuse is detected.

Your tasks

2.1
Add FamilyId and ReplacedByToken to RefreshToken, plus the methods that maintain them.
Domain work — keep it rich. User.IssueRefreshToken starts a new family; a rotation method continues one. Don't let a caller set FamilyId freely.
2.2
Register + login through UserManager, issuing a JWT that carries your UserRole as a role claim.
Carry over from the old repo: ClockSkew = TimeSpan.Zero, fail fast when the JWT key is missing, key in user-secrets. Login failures must not reveal whether the email exists.
2.3
Refresh endpoint: revoke the presented token and issue its replacement in one transaction.
If those are two separate saves, a crash between them either logs the user out or leaves two live tokens. Neither is acceptable.
2.4
Reuse detection: presenting a revoked token revokes its whole family and returns 401.
2.5
Authenticated logout that revokes only the caller's tokens. Change display name and password.
"Only the caller's" — write the test where user A sends user B's token and gets nothing.
2.6
Registration returns 201 Created with a location header.

Done when

A refresh returns a new refresh token, replaying the old one kills the session, and there is a test proving both. If you can replay a token twice and stay logged in, you have rotation without detection — which is the failure this phase exists to prevent.

PHASE 3 after 2

CQRS, and what a pipeline buys you

Plan reference: M3-01 through M3-05. You're changing shape, not behaviour — start with Products, which already works, so any difference in output is a bug you introduced.

New concepts in this phase

CQRS

Commands change state and return little; queries return data and change nothing. Separating them lets each side be optimised without compromise.

Mediator pattern

A controller sends a request object and doesn't know which class handles it. GoF pattern; MediatR is one implementation of it.

Pipeline behavior

Middleware for handlers. Write a cross-cutting concern once instead of editing thirty handlers — this is the actual payoff.

Vertical slice

Organise by feature, not by technical layer. All of "place an order" in one folder beats spreading it across five.

Your tasks

3.1
Convert Products first: one command or query per use case, one handler each.
Products already works. Any behaviour change is your bug, which makes it the safest place to learn the shape.
3.2
Write the validation behavior. Now wire FluentValidation — once, here.
3.3
Write the logging behavior: handler name, duration, outcome.
3.4
Convert Cart, Addresses, Auth.
Watch what happens to the Cart handlers — most of the logic is already in Cart. A handler that just loads, calls one method, and saves is the sign your Phase 0 work paid off.
3.5
Audit every controller action for business if statements. There should be none left.

Done when

No controller action contains an if about a business rule, and adding a cross-cutting concern means writing one behavior rather than editing every handler.

PHASE 4 the real one

Checkout — money, races, and messages that arrive late

Plan reference: M4-01 through M4-17, plus my two additions from correction 5. This is the phase with no existing code to lean on and the only phase where getting it wrong costs real money.

New concepts in this phase

Optimistic concurrency

Don't lock — detect. Read a version token, write conditionally on it being unchanged, and handle the loser.

Idempotency

The same request twice produces one effect. Required whenever the network can retry, which is always.

Webhook

The payment provider calls you, later, possibly twice, possibly out of order. Signature verification is not optional.

Eventual consistency

The order is Pending and correct. It becomes Confirmed when a message arrives. Nothing blocks waiting.

Transaction boundary

Stock decrement, order insert, and cart clear either all happen or none do.

PHASE 5 continuous

Tests — and why this phase shouldn't exist

Plan reference: M5-01 through M5-05. Here's my one structural disagreement with your plan: a testing phase after the feature phases is a phase for writing tests that pass. Tests written after the fact document what the code does; tests written alongside it find out whether the code does what you meant.

What I'd change

  • Set up the test project at the end of Phase 1, once WebApplicationFactory has something to boot. Not as a phase — as infrastructure.
  • M5-01 (domain unit tests) is already half-written. The 54 checks I ran against your entities are exactly these tests. Port them to xUnit and it's done — that's an hour, not a phase.
  • M5-04 moves into Phase 4 as task 4.6, where it can still change the design.
  • What stays here: the integration suite over the full checkout flow with Testcontainers, and the webhook idempotency test.

New concepts in this phase

Test double vs real dependency

Substitute what you don't own. Don't substitute the database — an in-memory provider passes tests that Postgres would fail.

Testcontainers

Spin a real Postgres in Docker per test run. Your jsonb column and xmin token cannot be tested any other way.

WebApplicationFactory

Boots your real pipeline in-process — middleware, DI, filters — so you're testing the app, not a stub of it.

Mutation checking

Break the code deliberately and confirm the test fails. A test that passes against broken code is decoration.

PHASE 6 later

Containerise and deploy

Plan reference: M6-01 through M6-06. Nothing to correct here — this phase is well-sequenced. Redis belongs exactly where you put it, because this is the first phase where docker compose exists to run it.

New concepts in this phase

Multi-stage build

Build with the SDK image, ship with the runtime image. The final image contains no compiler and no source.

Distributed state

An in-memory rate limiter stops working the moment you run two replicas. This is a correctness argument, not a performance one.

Migration strategy

CI step or guarded startup migration. Both are defensible; running them unguarded on every instance start is not.

Build once, deploy many

The same image goes to every environment; only configuration differs.

PHASE 7 later

Polish

Plan reference: M7-01 through M7-05. Optional, and worth doing only on a deployed app where you can measure the difference. Optimising before you can measure is how you learn the wrong lessons.

Keyset vs offset pagination

OFFSET 10000 makes the database count 10,000 rows it will throw away. Learn why, even if you ship offset.

Trigram / tsvector search

LIKE '%term%' cannot use an index. pg_trgm GIN or a generated tsvector can.

Cache-aside

Read cache, miss, read database, populate, return. The hard part is invalidation on write, not the read.

Projection

Select into a DTO in the query so the database returns three columns, not thirty, and EF tracks nothing.

Do this first, before any of it

Turn on EF query logging and look at the SQL your catalogue endpoint actually generates. Nine times out of ten the win is a missing AsNoTracking or an accidental N+1, not Redis. Measure, then optimise — and keep the before-and-after numbers. They're the most interesting thing you'll be able to say about this project.
